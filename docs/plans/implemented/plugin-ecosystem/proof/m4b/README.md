Stripped `tmux-drive.sh` captures at 160x45, from a fully isolated run: a private tmux socket, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, `-config` and `SIDECAR_ISOLATED_STATE=1` all under `/tmp/m4b-proof/run`, with `./scripts/tmux-drive.sh paths` confirmed before the run and `stop` after it. Nothing resolved under `~/.local/state/sidecar` or `~/.config/sidecar`.

The binary was built from this worktree and passed as `SIDECAR_BIN`. The plugin is `internal/pluginhost/testdata/fixtureprovider`, built from this worktree and configured as one `plugins.external` instance with `plugin_protocol` on. Its `results` collection declares the three filter shapes M4b added — `scope` (a choice with a default, and so the collection's scope), `source` (a choice with none), and `since` (text) — and three of its list queries stand in for data the fixture's ordinary page does not have: `coverage` returns a degraded page with `omitted` and a 13-row `coverage[]`, `failed` returns the `failed` outcome, and any other word returns three answered rows.

## Compared against the mockup

`mockups/recall-studio.scope-picker.txt` is the screen capture 01 implements. What matches: the modal's title (`View · Results`), `Current sort:` above the sort list, the sort keys with the live one marked, the filters after them in declared order, `Done` last, and the pill on the title row carrying the applied scope. What differs, and why:

1. **The mockup draws every filter as a radio row in one flat list** (`( ) source · any`, `(x) type · note`, `(x) since · 2026-08-01`), including `since`, which is a date. The implementation draws a labelled control per filter and gives `since` a text input, because the protocol's `kind: "text"` is a value the user types and a radio group cannot express one. The mockup was drawn before `filters[]` had kinds.
2. **The mockup's rows read `type · note`** — the filter's id and its value in one row. The implementation puts the filter's label on its own muted line above its control and the choice titles in the control, which is how every other modal in Sidecar labels a group (`internal/modal`'s `Custom` label plus `List`), and what lets a 64-choice filter scroll inside its own section rather than pushing Done off the box.
3. **The mockup's pill reads `⇅ rank · 3 filters`**; the implementation reads `⇅ Relevance · This project · 1 filter`. The decision the plan settled after the mockup was drawn is that the scope is always visible *by name* — "3 filters" does not tell a reader what the page covers — so the scope's title is shown and only the others are counted.
4. **The mockup shows the sort key by id (`rank`)**; the implementation shows the declared label (`Relevance`). The label is what the plugin asked to be shown, and the pill has always used it.
5. **The modal is centred over the whole frame rather than over the list box.** That is `ui.OverlayModal`'s placement, shared with every other modal on this surface; the mockup drew it over the list because it was drawn by hand.

`mockups/recall-studio.results-degraded.txt` is the screen capture 03 implements, and the two agree on the notice row, the `r  retry` affordance, and the summary line. It differs in one way: the mockup writes the suppressed count as a second free-text notice (`•  2 records suppressed below the relevance floor`), where the implementation renders `omitted` as data on the summary row and in the modal. That is the revision the mockup surfaced, applied.
