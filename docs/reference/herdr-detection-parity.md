# Herdr detection parity: vendored tree, lock, and regex compatibility

Reference for the vendored Herdr agent-detection manifests and what was measured about them. The plan is `docs/plans/active/herdr-detection-parity.md`; this document records facts, not intent.

## Vendored tree and lock

`internal/agentactivity/manifests/upstream/` holds byte-for-byte copies of Herdr's 21 agent-detection manifests plus the published catalog `index.toml`, an Apache-2.0 `NOTICE`, and Herdr's `LICENSE`. They come from Herdr commit `e2b85c73615b37a483eefa839923d9aff8e629b3` (`e2b85c7`) at `https://github.com/herdrdev/herdr`, cross-checked against the live catalog at `https://herdr.dev/agent-detection/index.toml`. The differential harness in later phases runs against Herdr release `v0.8.2`, which is recorded in the lock as `pinned_release_tag`.

`upstream.lock.json` pins every file: sha256, byte length, manifest version, `min_engine_version`, rule count, alias list, whether the bundled or the published copy won and why, and any regex pattern in that file which Go's RE2 cannot compile. Its `files` section pins the two vendored files that are not manifests, `upstream/LICENSE` and the generated `upstream/NOTICE`, by the same sha256 and byte length. `TestVendoredManifestsMatchLock` hashes each embedded manifest against the lock and `TestVendoredAttributionFilesMatchLock` hashes those two, so a hand edit to any vendored file fails CI. Edits belong in an overlay under `internal/agentactivity/manifests/sidecar/`; see the README there.

Per-agent the tool chooses the copy a Herdr client would load: the published one unless it is older than the bundled one. Nineteen agents have identical published and bundled versions and the published copy is vendored. Two are exceptions, both of them deliberate upstream:

- `grok` — bundled `2026.07.16.2` (engine 3) is newer than published `2026.07.16.1` (engine 2), so the bundled copy is vendored. Herdr stages the older published copy on purpose to keep engine-2 clients working; its own checker carries an explicit exception for it.
- `muse` — bundled only at `2026.08.26.1`. Herdr does not publish it until a stable binary can identify the process.

`aliases.upstream.json` carries Herdr's `lookup_agent` table (23 agents), the `is_generic_runtime_or_shell` list, the `python[N[.N]]` rule, the `muse-bin-<digit>` versioned-binary prefix, and the suffixes `normalized_agent_lookup_name` strips. `authority.upstream.json` carries Herdr's published per-agent authority table with each provider's `HERDR_INTEGRATION_VERSION`: six agents where hooks are the state authority (`kilo`, `kimi`, `mastracode`, `omp`, `opencode`, `pi`), eleven where the integration supplies session identity only, and six with no integration. Both are extracted by regex over stable Rust and MDX shapes, and the extractor fails loudly rather than writing an empty table if a shape changes.

### Re-syncing

```bash
scripts/sync-herdr.sh                                        # Herdr's default branch + live catalog
scripts/sync-herdr.sh --ref preview-2026-08-31-b1ff4582e968   # pin to a release tag by hand
scripts/sync-herdr.sh --source-dir ~/code/herdr --ref e2b85c7 # a local checkout, live catalog
scripts/sync-herdr.sh --source-dir ~/code/herdr --offline     # no network at all
```

The wrapper is a thin shell over `go run ./internal/tools/herdrsync`. With `--source-dir` it reads every file with `git show <ref>:<path>` inside that checkout rather than off the working tree, and refuses to run when `--ref` does not resolve there, so the bytes vendored are always the bytes of the commit the lock and the `NOTICE` record. It writes under two roots and no others, `internal/agentactivity/manifests` and `internal/agentintegration`, caps every fetched file at 256 KiB the way Herdr does, validates every file before writing anything, and refuses the whole sync if a file fails validation or declares a `min_engine_version` above `manifest.EngineVersion` (3). It renders `report.md` next to the lock; that file is committed, because it is the review surface for a sync and its diff is the fastest way to see what upstream changed.

With `--offline` the published copies come from `<source-dir>/distribution/agent-detection` rather than herdr.dev, the ETag is recorded as `unknown`, and the lock carries a note saying so. That keeps the published-versus-bundled decision reproducible without a network. The integration assets under `internal/agentintegration/upstream/` are vendored by the same pass; see "Vendored integration assets" below.

## Vendored integration assets

`internal/agentintegration/upstream/` holds Herdr's `src/integration/assets` verbatim at the pinned ref, in upstream's own directory shape: 34 files across seventeen provider directories plus the shared top-level `herdr-agent-state.test.ts`, with Herdr's `LICENSE` and a generated `NOTICE` beside them for the same Apache-2.0 reason the manifests carry theirs. These are hook scripts and plugins, not manifests; nothing at runtime reads them. They are here so that a bump in a provider's hook payload is a diff a maintainer reads rather than a discovery someone makes later, which is what [Phase 6](../plans/active/herdr-detection-parity.md) is built on.

The lock is `internal/agentintegration/upstream.lock.json`, embedded into `internal/agentintegration`, and it is deliberately a *second* lock rather than a section of `upstream.lock.json`. A lock is only enforceable by the package that embeds the files it pins, and a manifests-lock section describing files under `internal/agentintegration/` could not be checked by the manifests package's own test. It pins every file by sha256, byte length, upstream origin path and the `HERDR_INTEGRATION_VERSION` its directory declares, and per provider the id, the upstream directory name and the version its files agree on. `TestVendoredIntegrationAssetsMatchLock` walks the tree, so a hand edit, a removed file and an added unpinned file all fail CI.

Sidecar's own three assets record what they were ported from, in `internal/agentintegration/portedfrom.go`, as exported Go data rather than a header comment the sync tool would have to parse. Each record carries a `Version`, the Herdr `Commit` that version appears at, and an `Evidence` string saying where both came from, because the value is an inference about history rather than something anyone wrote down at the time. Today: OpenCode 10, Codex 8 and Claude 9, all at Herdr `4a3b04f59ba3b7d8a15cea187b23e1e80c343b0c`, argued from `docs/plans/active/notification-agent-lifecycle-hooks.md` recording that commit as the one inspected for provider assets, one day before the commits that created all three Sidecar assets, and corroborated for Codex by the live codex-cli trust-hash vector in `codex_install_test.go`. A record whose starting point cannot be established is the literal string `unknown`, which is what the plan prescribes; the report then prints the whole current upstream file instead of a diff.

The sync report uses those records to make a bump actionable. For a ported provider it renders the upstream diff since the version the port names, so re-porting is a review of a diff. For a provider Sidecar has not ported, the bump alone is the signal that the provider's hook payload moved. The comparison is on bytes rather than on version numbers, because a file edited without a version bump is exactly what a version comparison misses.

## Regex compatibility

The 21 vendored manifests carry **122 rules** and **83 regex patterns** (`regex` plus `line_regex`, counted across every nested gate).

**79 of 83 compile under Go's `regexp` (RE2). 4 do not.** All four failures are the same feature.

| File | Rule | Field | Pattern | Error |
| --- | --- | --- | --- | --- |
| `upstream/antigravity.toml` | `spinner_working` | `line_regex` | `^\s*[\u2800-\u28FF]+\s+\p{Alphabetic}+\w*ing\b` | invalid character class range: `\p{Alphabetic}` |
| `upstream/cursor.toml` | `spinner_working` | `line_regex` | `^\s*(⬡\|⬢\|[\u2800-\u28FF]+)\s+\p{Alphabetic}+\w*ing\b` | invalid character class range: `\p{Alphabetic}` |
| `upstream/kiro.toml` | `tool_spinner_working` | `line_regex` | `^\s*(◔\|◑\|◕\|●)\s+\p{Alphabetic}` | invalid character class range: `\p{Alphabetic}` |
| `upstream/qodercli.toml` | `spinner_working` | `line_regex` | `^\s*[\u2800-\u28FF]\s+.*\p{Alphabetic}` | invalid character class range: `\p{Alphabetic}` |

**Is there an RE2-equivalent rewrite?** Not an exact one, but a sound one. Rust's `regex` crate supports Unicode *binary properties* by name; RE2 supports only general categories (`\p{L}`, `\p{Nd}`) and scripts (`\p{Greek}`). Unicode `Alphabetic` is `L + Nl + Other_Alphabetic`, and RE2 has no `Other_Alphabetic`, whose members are combining marks and a handful of symbols. Every one of these four rules uses `\p{Alphabetic}` to mean "a spinner glyph followed by a word", so `[\p{L}\p{Nl}]` (or plainly `\p{L}`) matches every screen these rules are aimed at. The two spellings diverge only where an `Other_Alphabetic` character — in practice a combining mark — falls inside the run being matched. Where the pattern is `\p{Alphabetic}+` (`antigravity.toml`, `cursor.toml`) that means a mark anywhere in the word, not just at its start: a decomposed accented word such as `de` + U+0301 + `marrage` ends the RE2 run at the mark, where the Rust pattern runs through it. Where the pattern matches a single `\p{Alphabetic}` (`kiro.toml`, `qodercli.toml`) the divergence needs a mark in that one position: a status word that *starts* with one, or, for `qodercli.toml`'s trailing `.*\p{Alphabetic}`, a line carrying such a mark and no letter at all. Neither shape is how an agent renders a status word: terminals emit precomposed text, and no status word begins with a combining mark. The rewrite belongs in an overlay carrying the same rule id, not in the vendored file; the overlay mechanism arrives in Phase 1.

**One syntactic translation is applied, and it is lossless.** Rust accepts `\uHHHH` and `\u{H...}` as code-point escapes; RE2 spells the same thing `\x{H...}` and rejects `\u` outright. `manifest.TranslateRustRegex` rewrites those escapes before compiling. `\u2800` and `\x{2800}` denote the same single code point, so nothing about what a pattern matches changes. Eight upstream patterns use `\u`; another 17 already use `\x{...}` directly, which is why both spellings appear in the same corpus. The translation happens in the engine, never in the vendored bytes: `TestNoVendoredFileIsRewritten` asserts the `\u` escapes are still in the files.

**Syntax features present in the corpus, and whether the two engines agree.** Counts are patterns containing the feature, not occurrences.

| Feature | Patterns | Rust `regex` versus Go RE2 |
| --- | --- | --- |
| `\d` `\w` `\s` | 59 | Identical. Both are ASCII-only by default in Rust and always ASCII in RE2. |
| Literal non-ASCII characters | 38 | Identical. Both operate on UTF-8 and match by code point. |
| Character classes and ranges | 35 | Identical. |
| Alternation | 29 | Identical, but leftmost-first versus leftmost-longest differs for *submatch* extraction only. The engine asks whether a pattern matches, never which alternative won, so this cannot change a verdict. |
| `(?:...)` | 21 | Identical. |
| `(?i)` | 20 | Identical: Unicode-aware simple case folding in both. |
| `\x{...}` | 17 | Identical. |
| `\b` | 14 | **Differs at the edges.** Rust's `\b` is Unicode-aware (`\w` there is Unicode word characters for boundary purposes); RE2's `\b` is ASCII-only. The 14 patterns use it to close a Latin word such as `...ing\b`, where both agree. A boundary between two non-ASCII letters would differ; none of the corpus does that. `\b` behaviour is worth re-checking on any sync that adds a pattern applying `\b` to non-Latin text. |
| `\u{...}` / `\uHHHH` | 8 | Translated, losslessly, as described above. |
| Bounded repeats `{m,n}` | 5 | Identical. |
| `\p{...}` | 4 | **Incompatible**; the four rows in the table above. |
| `(?m)` | 2 | Identical: `^` and `$` match at line boundaries. |
| `(?s)` | 2 | Identical: `.` matches a newline. |
| `\A` | 1 | Identical. |
| Lazy quantifiers | 1 | Identical in what they match. |

No pattern uses lookaround or a backreference, which neither engine supports, so there is nothing to check there. `TestEveryVendoredRegexCompilesUnderGoRegexp` pins the four known failures by file, rule id, and field, so a *new* incompatibility fails CI on the sync pull request rather than surfacing as a silently dead rule in a user's pane.

## Read window

Measured against Herdr source at `e2b85c7` and confirmed on the 0.8.2 binary running headless on an isolated config/state directory and socket (a pane printing 2000 numbered lines in a 39-row pane returned lines 1963–2000: 38 rows, the bottom cursor row trimmed).

- The detection text is the tail of the terminal buffer, anchored at the bottom regardless of where the viewport is scrolled (`src/pane/terminal.rs:2801-2813`, `ghostty_recent_read_range`).
- N is the pane's own row count (`src/pane/terminal.rs:2616-2623`), falling back to 24 when rows are unreadable (`DEFAULT_DETECTION_ROWS`, `src/pane/terminal.rs:41`).
- Rows are wrapped physical rows (not unwrapped) and each row is right-trimmed (`ghostty_screen_row`, `src/pane/terminal.rs:2841-2865`).
- Trailing blank rows are trimmed after the window is selected; the window is not extended upward to compensate. Interior blank lines are preserved. Rows join with `\n` plus one trailing newline (`src/pane/terminal.rs:2767-2768`, `:3358-3372`).
- `whole_recent` is that text verbatim (`src/detect/manifest.rs:1297`); every other screen region derives from it. `top_non_empty_lines(N)` reads the same window from the top and returns the text up to the end of the Nth non-empty line, interleaved blanks included (`src/detect/manifest.rs:1372-1384`); it requires engine 3.
- `osc_title` is the last OSC 0 or 2 payload, capped at 256 chars, cleared by an empty payload; `osc_progress` is the last OSC 9 payload after `9;` (`src/pane/osc.rs:448-517`). Both are cleared when the pane's foreground agent changes. Under tmux `osc_progress` is always empty.
- The live detection loop and `herdr agent read --source detection` read the same function (`src/pane.rs:896`, `:2470`), so the CLI is not an approximation.

Sidecar consequence: `Observation` carries `PaneHeight` from tmux `#{pane_height}`; the engine's window is `ansi.Strip` → last `PaneHeight` rows (24 when unknown) → right-trim each row → drop trailing blank rows. Sidecar's `capture-pane` still fetches up to 600 lines of scrollback; the engine bounds the tail.

That order is load-bearing and it is upstream's. Trimming *before* windowing reaches further up the buffer than the pane can display, which is how a resolved historical prompt gets back into view; upstream trims after and never backfills, so a blank row inside the window costs a row of the budget. `TestReadWindowIsTheTailOfTheBufferAtThePaneHeight` and `TestReadWindowTrimsTrailingBlanksWithoutExtendingUpward` pin both halves.

**The newline that terminates a capture is not a row.** This was wrong in the first implementation and it silently removed the topmost visible row of every window. `tmux capture-pane -p -e -N -S -600` pads the visible region out to the full pane height, so the pane's blank cursor row arrives as a real empty row of its own *and* the capture still ends with `\n`; splitting on `\n` therefore yields one more piece than there are rows. Counting that piece made the window N pieces deep including the terminator, so taking the last N dropped the first real row. Measured on a 20-row pane: `clear; printf "TOPROW\nb\nc\n"`, captured 25 lines deep and read at `--rows 20`, printed `b`, `c` and the prompt with `TOPROW` gone. One trailing empty piece is now dropped before the window is taken; the blank cursor row itself is kept and still spends a row of the budget, which is why the 39-row measurement returns 38 rows. `TestReadWindowKeepsTheTopRowOfATmuxShapedCapture` is the regression, and `testdata/codex/trust_directory.txt` is padded to its declared 40 rows so the corpus carries a realistically shaped capture for the one rule that anchors on the window's first row.

## Alias parity

Upstream `lookup_agent` (`src/detect/mod.rs:193-222`) normalises before lookup: lower-case, trim, strip one of `.exe .cmd .bat .ps1 .js`, take the path basename across `/` or `\` (`src/detect/mod.rs:668-683`). Sidecar's `identifyProcessName` now does the same (`normalizeProcessName` in `activity.go`), with the Claude version-string argv0 checked on the un-normalised name so `1.2.3.js` cannot read as Claude.

| Family | Upstream aliases | Added to Sidecar |
| --- | --- | --- |
| claude | `claude`, `claude-code` | `claude-code` |
| antigravity | `agy`, `antigravity`, `antigravity-cli` | `antigravity-cli` |
| opencode | `opencode`, `opencode2`, `open-code` | `opencode2` |
| codex, grok, pi, copilot, cursor, amp, muse | as upstream | none needed; Sidecar is a superset for codex (`codex-cli`), grok (`grok-*`), muse (`muse-*`) |

Generic runtimes: Herdr's list is `sh bash zsh fish tmux node bun cmd powershell pwsh python[N[.N]]`. Sidecar returns `shell` for `sh bash zsh fish nu pwsh` and `""` for the rest; nothing on Herdr's list resolves to a Sidecar family (`TestHerdrGenericRuntimesNeverResolveToAProvider`). Sidecar's `shell` bucket is a launch-readiness gate, not Herdr's process-scoring predicate, so it is deliberately not widened to `node`, `tmux`, or `python`. The scoring predicate is a separate one, `isGenericRuntimeOrShell` in `process_tree.go`, and `TestGenericRuntimePredicateIsNotTheShellBucket` pins that the two lists differ in both directions.

## Process-tree scoring and the launch hint

Ported in Slice 3 of [the parity plan](../plans/implemented/herdr-parity-close-the-gap.md); `process_tree.go` is Herdr's `identify_agent_in_job` chain at `d08e4468`, function by function with a citation each. Sidecar matched `argv[0]` basenames only before it, so an agent installed as a plain `#!/usr/bin/env node` shim left the interpreter in `argv[0]`, tmux reported `node`, and the pane was never claimed.

The scan prefers the foreground process group leader and otherwise takes the best-scoring member, where the ladder is: 3 when unwrapping a runtime's argv renamed the process, 2 for a non-runtime, 1 for a runtime. The platform seam carries pid, ppid, comm, `argv[0]` and full argv, read in the same single process-table walk that previously produced `argv[0]` alone.

**A resolved identity settles which provider a pane is, in both directions.** `processGate` admits the provider the identity names and refuses every other one, including the four gates that accept a bare `node` or `bun` from `pane_current_command`. That second direction closed a hole rather than widening one: on a pane running Pi, `claudeProcess("node")` was true, so `claude.toml` was evaluable against a Pi screen. When nothing resolves — a platform with no process-identity adapter — the per-provider command rules are the whole gate, exactly as before.

**`SIDECAR_AGENT=<family>` is the launch-time hint**, Herdr's `HERDR_AGENT` under Sidecar's own name (decision 1 of the parity plan: Sidecar never claims to be Herdr through a `HERDR_*` variable). Export it on a wrapper command whose real process a sandbox or container hides, and the named family's manifest is used for that pane. Two rules bound it:

- **Process evidence beats the hint**, which is a deliberate divergence from upstream. Herdr reads the leader's hint before identifying the leader, which is safe for them because their own wrapper sets it; Sidecar's is a bare environment variable anyone in the session can set, so it answers only where evidence names nothing.
- **It is never a lifecycle claim.** `ResolveForegroundProcess` is evidence-only and is what `lifecycleenv.OccupantKind` — and so `VerifyReportedKind`, which *refuses* hook reports — reads. `ResolveForegroundAgent` is the hint-aware one and is read only by detection and the UI. Merging them would let `export SIDECAR_AGENT=codex` switch off a Claude pane's session binding. `TestAnAgentHintCannotChangeTheOccupant` pins it.

Unknown values are no hint rather than an error, and the value is validated through the same alias table as everything else.

**Reading a hint means reading another process's environment, and neither adapter can do that unconditionally.** Linux gates it by uid (`/proc/<pid>/environ`). macOS gates it by *binary*: a restricted executable — SIP-protected platform binaries, the same protection that blocks `DYLD_*` inheritance — has its environment section withheld from `kern.procargs2` for everyone, same uid included, while an ordinary binary's is readable cross-process. Measured on 2026-09-02 with two children of one test process, both carrying `SIDECAR_AGENT`: `/bin/sleep` read back 34 bytes with no hint, and a byte-identical copy of that same binary at an ordinary path read back 11356 bytes and yielded the hint. Argv crosses the boundary in both cases, which is why identification still works on a pane the hint cannot reach.

The practical bound is that `sandbox-exec`, `ssh` and the system shells cannot be hinted through on macOS; a wrapper the user installed — Docker, colima, nix, Homebrew — can. Upstream Herdr's `process_agent_hint` (`src/platform/macos.rs`) has the identical behaviour, so `HERDR_AGENT` is bounded the same way. **A live proof of this feature must use a binary you built**, or it reads empty for a reason that has nothing to do with the code.

What a pane pays to be identified is a three-rung ladder in `ResolveForegroundAgent`, which owns that decision so no caller has to repeat it. A command that already names an agent, or names a shell, reads nothing at all — an idle `zsh` pane costs zero. A command the alias table cannot place, which is what an unrecognised wrapper looks like, gets one foreground-group lookup plus one environment read **on the group leader only**: the group id is the leader's pid, and that is what makes the hint reachable without a process-table walk. Only a known shared runtime (`node`, `bun`, `agent`, `python*`) is worth the full walk, with the hint as its fallback. `TestTheIdentityCostLadderSpendsWhatThePaneJustifies` counts the walks per rung, so the claim is mechanical rather than asserted.

## Engine (Phase 1)

`internal/agentactivity/manifest` executes the vendored manifests at engine version 3: `ReadWindow` builds the detection window measured above, `resolve.go` implements all fifteen regions with a citation to the Herdr line each helper ports, `compile.go` compiles every regex once (after `TranslateRustRegex`) and marks an uncompilable rule as never matching with a `regex_incompatible` note in its explain evidence, `evaluate.go` runs every rule and keeps the highest priority with ties to the earlier rule, and `merge.go` applies a `sidecar/<agent>.toml` overlay by rule id. `internal/agentactivity/manifests.Load` compiles upstream plus overlay once per agent behind a `sync.Once`; a broken overlay becomes a diagnostic on the returned `Source` and upstream is used alone.

Three engine details are Sidecar's own and have no upstream counterpart, because Sidecar's inputs are not Herdr's:

- **The `osc_title` region is ANSI-stripped.** Herdr's `osc_title` is a decoded OSC 0/2 payload and carries no SGR by construction; Sidecar's is tmux `#{pane_title}`, which hands back whatever bytes the program wrote. Every upstream `osc_title` rule is anchored at the start of the title, so an unstripped escape ahead of a coloured spinner glyph turns the rule into a permanent no-match and a working pane reads as idle. On a title with no escapes the strip is identity.
- **`contains` folds with the full Unicode lowercase algorithm**, not `strings.ToLower`. Herdr uses Rust's `str::to_lowercase`, which applies SpecialCasing (U+0130 lowers to two runes) and the Final_Sigma condition (a Σ ending a word lowers to ς); Go's simple per-rune fold does neither, so a needle and a screen Herdr separates would match here. `golang.org/x/text/cases` with `language.Und` is used for both the needle and the region. No vendored needle diverges today; `TestContainsFoldsCaseTheWayRustDoes` is what keeps a sync from introducing one silently.
- **An uncompilable regex kills its whole rule, not just the pattern.** Inside a `not` gate that is the opposite of Herdr, which would evaluate the pattern, fail to match it, satisfy the `not` and usually fire the rule. Skipping is the safer direction and it is unreachable today: all four incompatible patterns are positive `line_regex` matchers with an overlay rewrite each, which `TestOverlaysMakeEveryRuleCompilable` enforces.

An overlay must declare the id of the manifest it amends; a mismatch is refused rather than merged, because the loader keys on the file name and the merged manifest keeps upstream's id, so nothing else would notice a misfiled overlay.

`conformance_test.go` ports 36 of Herdr's 45 inline manifest tests under their Rust names. The nine not ported are: six that exercise Herdr's *loader* rather than its engine, two duplicate cases covered elsewhere, and one loader-failure test whose analogue is `TestOverlayFailureFallsBackToUpstream`. The six loader tests are still not ported under their Rust names, and after Phase 5 that is a naming gap rather than a coverage gap: Sidecar has the remote cache those tests describe, and the equivalent assertions live in `internal/agentactivity/manifests/fetch_test.go` against Sidecar's own loader, which is vendored-plus-overlay under a fetched file rather than Herdr's flat three-source stack. `remote_manifest_loads_between_local_override_and_bundled` is `TestAFetchedManifestNewerThanTheVendoredOneBecomesActive`, `older_cached_remote_manifest_does_not_shadow_newer_bundled_manifest` is `TestAFetchedManifestOlderThanTheVendoredOneIsCachedButNotActive`, `local_override_shadows_cached_remote_manifest` is `TestALocalOverrideWinsOverAFetchedManifest`, `invalid_local_override_falls_back_to_cached_remote_manifest` is `TestAnInvalidLocalOverrideFallsBackToTheCachedManifest`, and `detection_uses_cached_manifest_until_explicit_reload` is `TestFetchInvalidatesOnlyTheAgentsWhoseCacheMoved`. The sixth, `fallback_explain_preserves_active_manifest_version`, is covered by the version fields `explain` and `sidecar agent manifests` report on every path rather than by one test of its own.

Eight overlay files exist today, carrying 22 rules between them. Four rules are the `\p{Alphabetic}` rewrites (antigravity, cursor, kiro, qodercli), each replacing the upstream rule id with `[\p{L}\p{Nl}]`; `TestOverlaysMakeEveryRuleCompilable` proves no merged manifest carries a dead rule, and `TestRewrittenAlphabeticRulesMatchTheScreensTheyTarget` proves each still matches the screen its original targets. One is a `disable = true` (codex `osc_title_idle`). The other seventeen are Sidecar-owned detection rules the Phase 2 cutover and its review kept or added, each with a fixture; see "Phase 2 cutover" below.

`sidecar agent explain --file PATH --agent KIND [--title T] [--rows N] [--print-window] [--json]` evaluates a saved screen (testdata header format or raw text) with no tmux and no store, printing Herdr's text layout or the JSON explain record. `--print-window` prints the exact window the engine saw, which is Herdr's `agent read --source detection` offline.

`--agent` takes any id Sidecar vendors a manifest for, not only the ten it claims as providers. A provider is evaluated the way a live pane is, process gate and all; an id with no provider — `kiro`, `qodercli` — is evaluated as a manifest through `agentactivity.ExplainVendoredManifest`, with no gate, no evidence string and no fallback policy, because none of those exist without a provider. That is what gives the two `\p{Alphabetic}` rewrites in those files a fixture, a census row and a differential-harness row; before the Phase 2 review they had none of the three, so a dead pattern in either would have stayed dead until someone read the TOML.

`--file` runs with no tmux, no lifecycle store and no running agent, but it is not hermetic: the manifest still comes from the loader, so a local override applies to it exactly as it does to a live pane. Two people running the same fixture can therefore reach different verdicts. The `manifest` line names the file that answered and a `warning` line names any that was refused, which is what makes that visible rather than confusing.

### Local overrides (Phase 3)

`~/.config/sidecar/agent-detection/<file>.toml` replaces the vendored manifest for one agent, which is Herdr's own precedence (`load_manifest_uncached`, manifest.rs:599 at e2b85c7) and gives the same tuning loop Herdr's `AGENTS.md` describes. It is the top of a four-source stack since Phase 5, not a three-source one: a valid local override, then the newer of the runtime fetch cache and the vendored file, with the Sidecar overlay merged onto whichever of those two won. An override that is refused drops to the next source *down*, which is the cache when there is a usable one and the vendored file otherwise, so "a broken override falls back" does not mean "a broken override falls back to the binary". Three things about it are not obvious and each has cost someone an hour somewhere:

- **The file is named after the vendored manifest, not after the agent label.** Copilot's override is `github-copilot.toml`, where Herdr's is `copilot.toml`; Antigravity's is `antigravity.toml` in both, though its manifest id is `agy`. Sidecar keys on the file it replaces, so there is one rule rather than two spellings that agree nineteen times out of twenty-one. `manifests.OverridePath` is the answer in code, `agentactivity.HerdrAgentLabel` is the Herdr-side spelling and is not this.
- **An override replaces the Sidecar overlay too.** It is not a third merge layer: the file you put there is the whole manifest for that agent. The consequence that bites is the four `\p{Alphabetic}` rules (antigravity, cursor, kiro, qodercli), whose RE2 rewrite lives in the overlay. Copy one of those vendored files into the override directory to tune an unrelated rule and the rewrite goes with the overlay, leaving upstream's uncompilable pattern in a rule that can now never match. That is why an override carrying a rule RE2 cannot compile loads with a warning naming the dead rules, rather than loading silently: the same dead rule inside a vendored file is covered by an overlay, and inside an override it is not.
- **A refused override is reported, never fatal.** Unreadable, unparseable, invalid, uncompilable, declaring no `id`, declaring another agent's `id`, or declaring a `min_engine_version` this engine cannot evaluate: each is ignored, the vendored manifest plus its overlay is used instead, and the reason rides the compiled manifest into `explain` as `warning`, on both the live path and `--file`. Two of those refusals are deliberately not Herdr's. The engine-version check is Herdr's remote-path rule applied to a local file, because copying a published manifest is how a user acquires one. And a dangling symlink is reported rather than read as "no override": Herdr cannot tell those apart, and a link into a dotfiles repository that has not been checked out is a plausible way to have one.

There is no hot reload. The file is read once per agent behind the same `sync.Once` that compiles the vendored manifest, so a running process keeps the manifest it started with, and `explain` reporting the loaded source is how a stale process is spotted.

### Runtime catalog fetch (Phase 5)

`detection.remoteManifests` in `~/.config/sidecar/config.json` takes `"off"` (the default), `"herdr.dev"`, or the http(s) URL of a catalog index. With it on, Sidecar reads Herdr's published catalog under Herdr's own rules, ported from `manifest_update.rs` at `e2b85c7`: a `schema_version = 1` index, a 256 KiB cap enforced on the bytes read rather than on a `Content-Length` the server supplies, validation through the distribution validator so a file with no `version` or a newer `min_engine_version` is refused, a downgrade refused, a same-version file whose bytes changed refused, and an atomic rename into `<state dir>/agent-detection/remote/<file>.toml`. The check runs in a `tea.Cmd` behind the first-ready-frame latch, never in `Init()`, and the status of the last one is in `<state dir>/agent-detection/status.json`, which `sidecar agent manifests` prints.

Six things about it are Sidecar's own, and each is a divergence from Herdr worth knowing before turning it on:

- **Off means off, cache included.** Herdr's loader reads its remote cache whatever the setting says; Sidecar's does not. The setting used to gate fetching alone, so a cache written during a week when it was on kept answering afterwards, `explain` kept reporting `active_source: remote`, and there was no way back to the vendored tree short of deleting a state directory by hand. A user turning a network feature off is asking the software to stop using what the network gave it. The bytes stay on disk, and `sidecar agent manifests` lists them in the REMOTE column under a `cache ignored` line, because "you have a fetched file and it is not the one running" is the one state the rest of the table cannot express.
- **There is a way out, and it is non-interactive.** `sidecar agent manifests --refresh` checks now, ignoring the once-a-day gate, and refuses with exit 2 when the setting is off rather than pretending to work. `sidecar agent manifests --clear-cache` deletes every cached manifest and the status file. Neither existed at first, and without them a user who changed the catalog URL, or whose day was claimed by a check that has since been fixed, had no recovery path at all. Changing the catalog URL also skips the day gate on its own: the day belongs to the catalog that claimed it.
- **The overlay is not optional, and a file it cannot merge onto is not cached.** An overlay carries Sidecar's own rules and the four `\p{Alphabetic}` RE2 rewrites, and it merges onto whichever upstream file won. If upstream renames or removes a rule id the overlay names, the merge fails - and the answer is to abandon the *fetched file*, not the overlay. `codex.toml` would otherwise lose six rules including the `osc_title_idle` disable, `claude.toml` five, `cursor.toml` four, and the un-rewritten `\p{Alphabetic}` rule would come back dead. So `commitFetchedManifest` refuses to cache such a file (`ignored`, with the merge error in the status file), and the loader falls back to vendored-plus-overlay for a cache written before that rule existed. Known-good detection beats a newer file with Sidecar's half stripped out; re-cutting the overlay is what lets the next check take it.
- **A dead rule in a fetched file is named.** A rule whose pattern RE2 cannot compile is skipped whole, so it asserts nothing. On the vendored path that cannot happen - every incompatible pattern has an overlay rewrite and `TestOverlaysMakeEveryRuleCompilable` proves it. On the fetched path it is exactly what upstream publishing a new `\p{Alphabetic}` rule looks like, and the sync report that would have named it has no human in the loop here. So the loader names the dead rules on the `Source` diagnostic and in the log, the way a local override's dead rules are named.
- **One unusable catalog row never refuses the index.** Herdr skips an id its own enum has no variant for before it validates the path; Sidecar keys on the path, so a row whose path does not resolve to a vendored manifest - unknown agent, unsafe path, not a plain `<name>.toml` - is skipped with a note in `status.json` rather than failing the whole check. Getting this wrong would have been permanent and silent: Herdr adds one row this binary cannot resolve and every other agent stops updating for good. What still refuses the whole index is a document-level problem: it does not parse, it declares a schema version this client does not implement, or it names one agent twice.
- **Redirects are pinned to the catalog's host.** `joinURL` refuses a catalog path naming another host, and a 302 would otherwise defeat that check entirely, so the client's `CheckRedirect` refuses a cross-host redirect and an https-to-http downgrade. Herdr inherits curl's default here.

Two of the fetch's own rules are worth stating because they are timing, not policy. The day's attempt is claimed *before* the network work rather than after, which is what makes the gate hold across two processes rather than only across sequential runs; the cost is that a process killed mid-check burns that day, and that is the safe direction, because the vendored tree is underneath and a crash loop must not become a request loop. A check that *failed*, though, retries after an hour rather than a day: a laptop opened on a train with no connectivity claimed the day at 08:40 and never tried again when the connection returned, and "claim the day" and "never retry a failure inside the day" are separable. Twenty-four attempts a day against a static file is the worst case.

### Differential harness

`scripts/herdr-diff.sh` runs every fixture with a `screen:` block through `herdr agent explain --file --json` (the 0.8.2 release binary, with `XDG_CONFIG_HOME` pointed at a throwaway override directory holding the vendored bytes) and through `sidecar agent explain --file --json`, and diffs `state`, `matched_rule.id`, and `fallback_reason`.

Both sides are isolated, and the Sidecar side has to be for the same reason the Herdr side is: it reads a local override directory too. Every `sidecar` call in the script is given its own config axis with `-config`, which is what `manifests.OverrideDir` derives from. The flag goes before the subcommand, because global flags are stripped ahead of dispatch (`stripGlobalFlags`, internal/cli/cli.go) and the subcommand itself does not know it. Without that, one developer's `agent-detection/codex.toml` turns the numbers below into thirteen disagreements, and these numbers are the only tripwire the harness has.

The harness has two modes and both are run.

**Default mode** points Herdr at the *vendored upstream file alone* while Sidecar runs upstream plus its overlay, and asks where the two knowingly differ. Result at `e2b85c7` against herdr 0.8.2, after the Phase 2 cutover, its review and the three overlay fixes that followed: **61 fixtures compared, 37 agree, 0 disagree, 22 overlay divergences, 0 redundant overlay rules, 2 with no Herdr oracle, 5 proof transcripts skipped.**

**`--merged` mode** assembles the same merged manifest Sidecar runs — upstream plus the overlay, by the same three rules `manifest.Merge` applies — writes it into Herdr's override directory, and asks whether Sidecar's engine executes *Sidecar's own rules* the way Herdr's engine would. The default mode cannot ask that: there, every `sidecar.` rule is a divergence by construction. Result: **61 fixtures compared, 59 agree, 0 disagree, 2 with no Herdr oracle.** Every overlay rule reaches the same verdict under Herdr's Rust engine as under this Go port, which is the strongest statement available that the overlay is data rather than a second engine.

Two limitations are forced by Herdr's `--file` mode: it passes an empty `osc_title` (`explain_for_label`), so the comparison is screen-only with the title stripped on both sides, and it applies no read window, so the harness feeds both engines the window Sidecar prints with `--print-window`.

A fixture whose Sidecar verdict comes from a rule id beginning `sidecar.` is reported in default mode as an **overlay divergence**, not a disagreement, and does not fail the run. Herdr is being run against the vendored file alone, so a Sidecar-owned rule firing is the divergence the overlay exists to create and the fixture beside it is the evidence. The inverse is a failure: a `sidecar.` rule that reaches the *same* verdict Herdr reaches without it is reported as **redundant**, which is the plan's "overlay changes nothing" signal that the rule should be deleted. Redundancy is measured on the state and the fallback reason alone, because the two rule ids can never be equal — folding the id in made `REDUNDANT` unreachable, which is a defect the Phase 2 review found and fixed. An overlay rule carrying an *upstream* id — the four `\p{Alphabetic}` rewrites — is not in either bucket: those rules are live on Herdr's side too, so they must agree.

Two rows are neither, and both are declared rather than inferred:

- **`TITLE-ONLY`.** A `sidecar.` rule whose only effect is a title-versus-screen conflict cannot be judged by a harness that blanks the title on both sides: it reaches the same verdict Herdr reaches on every fixture the harness can see, and looks redundant when it is not. An overlay declares such a rule with a `# harness-exempt: sidecar.<id> — reason` line, and the script reads that whitelist. One rule uses it: grok's `sidecar.working_footer`, whose case is `TestGrokBusyChromeBeatsIdleTitleForm`, run with the title intact. The whitelist is keyed by the overlay file that declares the exemption, not by rule id alone, because an id is not unique across agents — `sidecar.overlay_retain` exists in both `claude.toml` and `grok.toml` — and an unscoped list would silence the redundancy check for one agent's rule because another agent's rule of the same name is exempt. The id pattern allows dots for the same reason it must: every such id contains at least one.
- **`NO-ORACLE`.** Herdr 0.8.2 has no manifest for the agent at all, so there is nothing to compare against. Two rows, both Muse: `muse/trust_workspace.txt` and `muse/thinking.txt`. Herdr ships `muse.toml` bundled-only and the 0.8.2 release predates it, which is exactly why it is vendored from the source tree rather than the published catalog.

Read the 37 default-mode agreements as a floor, not a proof of full parity. Many are fallback-versus-fallback — no rule matched on either side, so what agrees is the fallback, not a rule — and because the title is blanked on both sides, every `osc_title` rule no-matches on both engines, so a title-driven disagreement cannot show up here at all. The fixture census below, which runs with titles intact, is what covers that half.

### Rules dropped rather than carried

Not every rule was worth keeping, and the ones that went are as much of the result as the ones that stayed.

- **`cursor.screen.activity-working`** — an alternation over "running command", "working…", "starting…" and similar phrases anywhere in the bottom ten lines. No fixture, no upstream counterpart, and every phrase in it is one a turn can print *about* its own work, which is how a finished turn that narrated "running command" kept a pane on the working lane.
- **`grok.overlay.viewer` and both Antigravity retain rules** — retain rules keyed on "transcript", "conversation history", "esc to close" or "select a model". None had a fixture, and nothing in either provider's captures shows the CLI rendering such a viewer at all; all three were copies of Claude's rule written before the provider was harvested (`testdata/antigravity/availability.txt` records that no runtime states were captured in Phase 1). A retain rule that fires on a screen the provider may not paint freezes the badge for `SkipRetentionCap` on nothing, which is worse than the gap it fills.
- **The wide half of `grok.screen.blocked` and `antigravity.screen.blocked`** — alternations where any one of six to eight phrases ("Would you like to", "Allow .*?", "Proceed", "Amend", "enter.*Confirm") was enough to call a pane blocked. Upstream's blockers each require a corroborating pair from the same footer, which is what stops a turn quoting one of those phrases from reading as an unanswered prompt.
- **`grok.screen.working`'s "Thinking…" and "Waiting on " branches** — matched anywhere in the current-bottom window, where upstream's `spinner_status_working` requires the braille frame *and* the trailing `[stop]` chip on one line. A finished turn's last status line still says "Thinking…" for as long as it stays on screen, which is exactly the residual-working case `TestGrokIdleFooterBeatsResidualThinkingInViewport` was written for.
- **`muse.title.working`** — a braille frame in the pane title read as working, and upstream has no `osc_title` rule for Muse at all. Dropped rather than overlaid: no fixture captured it, upstream describes Muse's activity in terms of the `esc to interrupt` hint `working_esc_interrupt` reads, and inventing a title rule for a provider whose manifest upstream has not published yet is the speculative-rule mistake this cutover is removing elsewhere.
- **`muse.screen.working` and `muse.screen.blocked`** — the bare words "Thinking" or "Working" anywhere in sixteen lines, and an eight-way blocked alternation including "Proceed?" and "approve". Upstream's rules are pairs, and its own evidence note says why: Muse emits any one of those phrases as ordinary assistant text after a completed turn.

The Phase 2 review asked for the reason behind eight more drops that the cutover had made without recording one. Each is below with the reason it stays dropped, except `muse.screen.thinking-glyph`, which is the one the review restored (see the overlay table). The pattern in most of them is the same: the rule's basis was a *string* in a package harvest rather than a *screen* in a capture, and a rule written from a string is the speculative rule this cutover exists to remove.

- **`cursor.screen.write-blocked`'s and `cursor.screen.web-edit-blocked`'s no-control-line branches** — "Write to this file?" corroborated by "Add to allowlist" or "reject & propose changes" *without* the "Proceed (y)" upstream's `write_file_approval` also requires. Those two strings are in the cursor-cli 2026.08.04 harvest; a screen rendering either of them with no `(y)` or `keep (n)` control line is not. Every approval prompt in the corpus (`blocked_compatibility`, `blocked_shell`, `blocked_delete`, `blocked_web`) renders one, which is what upstream's rule is built on. Cursor's no-match fallback is low-evidence, so if such a screen does exist the pane reads as an unknown idle that cannot announce a completion, rather than as a finished turn — the gap is a missing blocker badge, not a false "done". A capture of the shape is what would justify an overlay rule.
- **`cursor.screen.spinner-working`'s past-tense and bare-label branches** — `⬢ Thought 3s` and the explicit Thinking / Working / Running / Searching labels beside a spinner. Past tense is what a *finished* step prints, and `working_spinner.txt` shows all three forms on one screen because that is how Cursor renders a step list: completed rows above the live one. Upstream's `\w*ing\b` matches the live row and ignores the finished ones, which is the correct reading of that screen; a rule that fires on the finished rows keeps a settled pane on the working lane, which is the residual-working failure the grok rules below were also narrowed for.
- **`grok.screen.blocked`'s `Allow .*\?` and `Enter to confirm` branches** — the one shape in that alternation that was a plausible pair (`Allow bash(…)?` above an `enter Confirm` footer) rather than a bare phrase. Writing the rule from the deleted alternation would be inventing a screen for the one provider whose title rule punishes a wrong guess. This is the highest-value capture left to take: a live Grok 1.0 permission prompt, and then an overlay rule with the fixture beside it.
- **`grokFooterCancel`'s wider cancel spellings** — the deleted footer resolver treated "esc to cancel" and "esc to interrupt" as cancel hints alongside "Esc:cancel" and "Ctrl+c:cancel"; `sidecar.idle_footer`'s `not` gate carries only the last two. - **The `background tasks?:\s*[1-9]` working branch in both `grok.screen.working` and `antigravity.screen.working`** — the same speculative pattern copied into two providers' tables. Neither `testdata/grok/` nor `testdata/antigravity/` has a capture containing the string, both providers' `availability.txt` record that no runtime states were harvested in Phase 1, and upstream reads the chip both CLIs actually render in a different spelling entirely: grok's `background_work_chip_working` matches `[⋅:⸬⁙.·]\s+[1-9][0-9]*\s+│` on the pinned top row and antigravity's `background_tasks_working` matches `·\s*[1-9][0-9]*\s+task`. Two rules for a string nobody has seen, when the shape that is attested is already covered.
- **`muse.overlay.retain`** — "esc to close", "model picker" or "select.*model" anywhere in twenty-four lines retained the pane's state. Upstream's `menu_overlay` is the same behaviour with corroboration: it requires a *pair* of footer controls ("enter confirm" + "esc go back", "space toggle" + "esc close" + "type filter") from Muse's own overlays, which is what keeps a turn discussing a model picker from freezing the badge for `SkipRetentionCap`.

### Two decisions the overlay spot-check settled

**The interrupted Codex screen resolves to the fallback, not to the composer idle.** With `sidecar.working_chrome` carrying upstream's `■ Conversation interrupted` gate, a screen showing a stale status line, the banner beneath it and the composer beneath that matches nothing: this rule is gated off by the banner, and `sidecar.composer_idle` is gated off by the interrupt hint the stale status line still carries. The pane reads `codex.known-live-fallback`, a low-evidence idle that establishes the lane without announcing a completion. The alternative considered was to let the banner cancel `sidecar.composer_idle`'s own interrupt gate, which would make this an explicit visible idle. It is rejected because the same edit fires on a banner still in the scrollback above a turn the user has since restarted, and an explicit visible idle mid-turn is the false "done" the whole overlay exists to prevent. One unannounced completion on an interrupted pane is the cheaper error. `TestCodexWorkingChromeRefusesInterruptedAndQuotedStatusLines` pins both halves.

**Muse's composer marker cannot be the gate that stands `sidecar.thinking_working` down.** The obvious reading of "a stale `◈ Thinking` above a drawn composer is idle" is a `not` on `^\s*⟩`, and it is wrong here: Muse keeps the composer drawn *during* a turn, which is the premise the rule rests on, and `thinking.txt` shows two `⟩` rows on a working screen. A `not` on the marker deletes the rule rather than narrowing it. What separates the settled screen from the live one is the completed status row, so that is what the gate reads — see the overlay table row above for the nesting and why it is not flat.

### A consequence of Herdr's visibility semantics, recorded

The engine takes `VisibleBlocker`, `VisibleWorking` and `VisibleIdle` from the matched rule's own `visible_*` flags rather than deriving them from the state, which is Herdr's semantics and what the plan adopted ("visible flags come from the matched rule"). Two upstream rules declare a blocked state with no `visible_blocker`: claude's `legacy_no_prompt_blocker` (300) and codex's `weak_blocker` (600). A pane matching one of them lands on the blocked lane but carries no attention flag, so `Tracker.VisibleBlocker` stays false and the surfaces that key an alert on it stay quiet. That is deliberate upstream — both are weak, high-recall rules meant to classify rather than to interrupt.

**Both rules are now overlaid to nag.** The engine is still not changed: the two overlays replace the upstream rules *by id*, copying them verbatim and adding `visible_blocker = true` and nothing else. Before the cutover every blocked verdict Sidecar minted raised the attention flag, and the screens these two rules are the last resort for are questions waiting on the user — "waiting for permission", "do you want to allow this connection?", a bare `[y/n]`, a "would you like to" beside a yes option. A blocked lane nobody is told about is a pane sitting on a question. Because the id is upstream's, `scripts/herdr-diff.sh` still classifies both rules through its AGREE path and requires the same state and the same rule id as Herdr reaches without the overlay — visibility is not compared, which is precisely why the rest of each copy must stay verbatim, and what would catch a re-sync that changed either rule underneath us. `testdata/claude/legacy_permission_wait.txt` and `testdata/codex/weak_blocker.txt` are the fixtures, and `TestWeakBlockersKeepTheAttentionFlag` asserts the flag. Delete either overlay if a captured screen shows the nag is wrong — a shape the rule reaches that is not a question waiting on the user.

### What the review of the cutover changed

The cutover was reviewed as a whole once every provider was on the manifest lane, and it found three regressions the per-provider work had introduced or left behind, plus a set of rules that had been dropped without a recorded reason. All of it is folded into the tables above; this is the list, in the order it cost the most.

1. **A Codex turn read as idle in the middle of a tool call.** `sidecar.composer_idle` matched the `›` the composer draws *during* a turn, upstream's `screen_working_fallback` reads three non-empty lines and one tool call's output pushes the status line to the fourth, and nothing else matched — so a plain or lagging title produced an explicit visible idle and the tracker announced a completed turn mid-turn. Fixed by the `not` gate on the interrupt hint and by `sidecar.working_chrome`. This is the same failure the whole plan opened with, reintroduced by a rule written to prevent it, which is the argument for the differential harness and the census being run over *new* fixtures rather than only the ones that already exist.
2. **An Antigravity permission prompt read as a completed turn**, because upstream's corroborators are not what the 1.1.11 CLI renders and this is the one provider whose fallback is full-evidence. Fixed by `sidecar.permission_prompt_blocked`. The same review re-examined the full-evidence fallback itself and kept it, for the reason recorded above.
3. **`Identify` lost screen identity on any pane taller than 24 rows** after a fresh start or a `/clear`, because `identityWindow` was built on `manifest.ReadWindow`, which windows before it trims. Fixed by trimming first, which is what the pre-manifest `RegionCurrent` did; the claim that `ReadWindow` matched `RegionCurrent` was wrong and is corrected in this document.
4. **Two rules rested on an argument rather than a gate**, and were given the gate: `sidecar.finished_background_tasks_idle` now loses to a live spinner instead of arguing that one cannot be on screen, and `sidecar.trust_prompt_blocked` reads twelve lines instead of the whole window so an answered prompt cannot report a blocker above a live turn.
5. **Eight rules had been dropped with no recorded reason.** Seven stay dropped and the reason for each is in "Rules dropped rather than carried" above; one, `muse.screen.thinking-glyph`, was restored as `sidecar.thinking_working` because Muse's two upstream idle rules are both `visible_idle` and a thinking pane matched one of them.
6. **`kiro` and `qodercli` had overlays with no coverage of any kind.** They have a fixture each now, and the census and the harness both read them.

The one gap the review named and left open was grok's: an `Allow …?` permission prompt with an `enter Confirm` footer is not covered by upstream's four blockers, and grok's `osc_title_idle` is a visible idle, so such a screen can announce a completion. It was closed below without a capture, and the reasoning for accepting that is in the next section. The capture has since been taken, and it shows the gap was never real: see "What the Grok capture measured".

### Three overlay fixes after the review

Three things were fixed after the review, on the branch and before the merge to main. All three are in the tables above; this is what each of them was.

1. **A Claude main loop waiting on background subagents read idle**, reported by the user from a live 2.1.257 pane. Claude paints two signals for that state and upstream reads neither of them where 2.1.257 puts them: `background_agents_working` reads the single last non-empty line above the prompt box, which on the captured screen is an `✔ Update installed · Restart to update` banner, and `background_shell_working` reads the footer for `· N shells ·` where 2.1.257 writes `· ← 3 agents ·`. The pane resolved to `live_prompt_box`, an *explicit visible* idle, so the tracker announced a completed turn while the subagent was still running. Fixed by `sidecar.background_agents_waiting` (966) and `sidecar.background_agents_footer_working` (965), with `testdata/claude/waiting_background_agents.txt` — a real capture — and `testdata/claude/background_agents_footer.txt`. The adversarial case is what shaped the first rule: `above_prompt_box` is unbounded upward and the capture's own scrollback carries two older waiting rows, so an unbounded rule would have reported working over every turn that followed them, forever. `TestClaudeStaleBackgroundAgentEvidenceDoesNotHoldTheWorkingLane` is that case, and it also pins the 2.1.220 `background-agents.txt` verdict, which must not move.
2. **Grok's `Allow …?` prompt is covered, from the deleted rule rather than from a capture.** This reverses the review's decision to leave it open, and the argument for reversing it is the asymmetry the review itself recorded: grok's idle rule is a *visible* idle, so the cost of no rule is a false "done" on an unanswered permission prompt, while the cost of a wrong rule is an attention badge on a pane that does not need one. `sidecar.allow_prompt_blocked` (1130) requires the question line *and* a control line beneath it, gated `not` on Grok's live cancel footer, and both halves come from the deleted `grok.screen.blocked` rather than from imagination. The fixture says **synthetic and unproven** in its own header and the rule's comment says a live capture replaces it. `TestGrokAllowPromptBlocksOnlyWithItsControlLine` carries both negatives: the question quoted in a transcript with no control line reads idle, and both lines above a live footer read working. **The capture has since been taken, it retired the rule, and the rule is now deleted** — see "What the Grok capture measured" below. The fixture named here is now that real capture.
3. **The two weak blockers keep Sidecar's attention flag**, as described in the section above.

What was *not* fixed at the time was the capture itself, and that is the one thing this document no longer has to hedge: a live Grok permission prompt has now been photographed, and the section below is what it showed. Every overlay rule in the corpus now rests on a capture or on an upstream literal; none is labelled unproven for its shape.

### What the Grok capture measured

Grok Build **1.0.13** (`5e9a58528b76`, stable), 2026-09-01, macOS, on an isolated tmux server (`tmux -L gc1` with a private `TMUX_TMPDIR`, 120x40) with `grok --permission-mode default` in a scratch directory. The account's Grok Build inference balance was exhausted (HTTP 402 on every model), so the tool call that raises a prompt was served by a local OpenAI-compatible endpoint declared as a `[model.*]` entry; everything on screen is drawn by Grok's own permission UI, from a `run_terminal_command` call for `echo hello` held open by an `ask = ["Bash(echo *)"]` rule. Nothing was approved.

**What the prompt renders.** A `┃`-guttered option dialog, numbered rows with `(●)`/`(○)` radio marks, above a single footer line, under a pane title that opens `⚠ Action Required`:

```
  ┃  print a greeting
  ┃  echo hello
  ┃  ← → narrow scope  ·  e edit pattern
  ┃
  ┃  1 (●) Yes, and don't ask again for anything (always-approve mode)
  ┃  2 (○) Always allow: echo
  ┃  3 (○) Yes, proceed
  ┃  4 (○) No, reject (type to add feedback)
  ┃  5 (○) Never allow: echo
  ┃

  1/5:select  │  Tab:next option  │  ←/→:scope  │  e:edit pattern  │  Ctrl+o:always-approve  │  Ctrl+c:cancel  │  Esc:
```

Title: `⚠ Action Required - ⠴ - print a greeting… - run the greeting command - grok`. The footer is truncated at `Esc:` by the 120-column pane.

The file-edit prompt is the same widget with a different option set, and it is the one that carries a literal `Allow` row — inside the gutter and with no `?`, so no rule looking for a bare `Allow …?` line can reach it either:

```
  ┃  Allow Edit to /…/probe.txt
  ┃
  ┃  1 (●) Yes, and don't ask again for anything (always-approve mode)
  ┃  2 (○) Yes, allow all edits during this session
  ┃  3 (○) Yes
  ┃  4 (○) No, reject (type to add feedback)
  ┃
  1/4:select  │  Tab:next option  │  Ctrl+o:always-approve  │  Ctrl+c:cancel  │  Esc:scrollback
```

**Verdict: the rule was unnecessary, and upstream already covers the screen.** On the captured shell-command prompt, `sidecar agent explain` reports `blocked` through `osc_title_blocked` (1300), with `option_dialog_blocked` (1200) and `permission_scope_selector` (1180) also matching. `sidecar.allow_prompt_blocked` (1130) does not match, and could not win if it did. Blank the title — which is the realistic adversarial case, because Sidecar reads `#{pane_title}` one repaint later than Herdr reads the OSC payload — and the screen alone still reports `blocked` through `option_dialog_blocked`. The only upstream blocker that misses is `permission_hints_blocked` (1190), which wants `ctrl+o:yolo` where 1.0.13's footer writes `Ctrl+o:always-approve`; the three that hit make that miss harmless.

**Where the guessed shape came from.** The deleted `grok.screen.blocked` matched `Allow .*\?` and `Enter to confirm`. The `enter confirm` string does exist in the 1.0.13 binary, in the `↑/↓ navigate · enter confirm · esc cancel` chrome of the resume-session and tools pickers. That is menu chrome, not a permission prompt, which is the most likely explanation for how the two halves came to be written as a pair.

**What changed as a result.** `testdata/grok/allow_prompt.txt` is now the real capture and reports `blocked` / `osc_title_blocked`; its header records the provenance instead of saying synthetic and unproven. `sidecar.allow_prompt_blocked` is left structurally unchanged at 1130 — rewriting it around the captured screen would only restate `option_dialog_blocked` at a lower priority — and its comment now says to delete it unless a Grok release is found that paints the old shape. **Deleting it is a separate decision and has not been taken here.** `TestGrokPermissionPromptIsCaughtByUpstreamBlockers` asserts the capture and the blank-title case; `TestGrokAllowPromptBlocksOnlyWithItsControlLine` keeps the rule's positive as a synthetic screen written in the test rather than as a fixture file, along with both of its original negatives.

One consequence not fixed here: `internal/agentactivity/testdata/README.md` still describes `grok/allow_prompt.txt` as synthetic and unproven, and `internal/agentactivity/manifests/report.md` (generated by `herdrsync`) still lists `sidecar.allow_prompt_blocked` as changing that fixture's verdict. Both are now stale.
